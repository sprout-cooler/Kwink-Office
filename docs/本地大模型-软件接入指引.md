## 0. 为什么零改动就能接（取证）

项目从设计之初就按 **OpenAI-compatible** 契约实现，代码里已有明确的本地/内网支持：

| 位置 | 证据 |
|---|---|
| `core/config.py` | 有 `LLM_BASE_URL` / `LLM_BASE_URL_CUSTOM` / `LLM_MODEL` / `LLM_API_KEY` 四个环境变量 |
| `core/settings_service.py` `AI_PROVIDERS` | 内置 `id: "custom"` 预设，label **「自建兼容端点」** |
| 同上 `ensure_url_scheme()` | 注释明写「自建服务（**Ollama / LocalAI / 内网 vLLM / Xinference**）几乎都是明文 HTTP」，内网 IP 自动补 `http://` |
| `app/tests/test_ai_url.py` | 已有 `http://localhost:11434/v1`、`http://192.168.1.10:8000/v1` 的协议头补全单测 |
| `modules/weekly_report/vlm.py` | `OpenAICompatibleRecognizer` 用裸 `urllib` 发 `POST {base_url}/chat/completions`，**无 SDK 依赖**（`requirements.txt` 里没有 openai 包） |
| 同上 | 图片以 `data:image/...;base64` 内联，不要求公网可访问的图片 URL |
| 同上 | `response_format=json_object` 遇 400 会**自动降级重试并记住**，兼容不支持该参数的端点 |
| `docker-compose.yaml` | `api` 与 `worker` 都注入了 `LLM_*` 变量；默认 bridge 网络可出站访问局域网 IP |

**协议级冒烟实测**（用项目真实识别器打一个假的 OpenAI 兼容端点）：

```
① 测试连接（设置页按钮）: True 连接成功
② 识别返回: task | 任务数: 1
③ 请求取证:
   path: /v1/chat/completions
   Authorization: Bearer ollama
   model: qwen2.5vl:7b
   response_format: {'type': 'json_object'}
   content 类型: ['text', 'image_url']
   image_url: data:image/png;base64,... 
```

结论：**协议完全对得上，填三个字段即可。**

## 1. 请求实际从哪个进程发出（排障用）

```
浏览器 → NAS 网关 → omnioffice-api 容器
                    └─ recognize_queue 的独立线程
                       └─ urllib POST http://<PC_IP>:11434/v1/chat/completions
```

- 识别是 `api` 容器内的**线程**（`recognize_queue._worker_loop`），不是 `worker` 容器、更不是浏览器直连。
- 所以**不需要**在浏览器侧配 CORS，也**不需要** PC 能反向访问 NAS。
- 排障时若连不通，应在 **api 容器内**测连通性，而不是在 NAS 宿主或你自己的浏览器里测。
- 每次识别都重新读库解析配置（`resolve_ai`），**改完设置立即生效，不用重启容器**。
  ⚠️ 例外：「识别并发数」需重启应用生效（设置页已标注）。

> ### ✅ 容器内实测已通过（2026-11-17，本机 NAS `192.168.31.204` / 镜像 1.0.43）
>
> 这是部署指引里"真机层"的关键一项，已实际在容器内部跑通（非宿主、非浏览器）：
>
> | 检查 | 结果 |
> |---|---|
> | `omnioffice-api` 容器（bridge 网 `172.18.0.5`）→ `http://192.168.31.182:11434/api/tags` | ✅ HTTP 200，见 2 个模型 |
> | `omnioffice-worker` 容器（`172.18.0.4`）→ 同上 | ✅ HTTP 200，见 2 个模型 |
> | **容器内 OpenAI 兼容层 + base64 图片真实识别** | ✅ **1.8 秒**，准确读出客户/任务/时间/状态 |
>
> 测试用的是周报模块**完全相同**的通道：`POST /v1/chat/completions` +
> `Authorization: Bearer ollama` + `image_url: data:image/png;base64,...`。
> 容器内镜像没有 curl，用 Python `urllib`（也正是项目识别器用的库）测试。
>
> 结论：**bridge 网络下容器能直连 PC 的 Ollama，无需改 compose 网络模式、无需 extra_hosts。**
> 剩下的只是软件设置页填地址，以及你自己的真实周报截图识别准确率验证。

## 2. 配置优先级（决定你在哪里填）

`resolve_ai()` 的优先级，**高 → 低**：

```
1. 模块覆盖   ai.<module>.<field>        ← 只影响周报模块（推荐用这层）
2. 全局默认   ai.default.<field>          ← 影响所有模块（周报 / 图片工具 OCR）
3. 环境变量   LLM_*（wizard 注入）
4. 内置兜底   BUILTIN_DEFAULTS（qwen3.8-flash 云端）
```

✅ **强烈建议用「模块覆盖」层**：只把周报切到本地模型，云端 Key 保留在全局层作为兜底。
这样本地模型不给力时，在设置里点一下「恢复继承全局」就能立刻切回云端，不用重新填 Key。

⚠️ 账号隔离：配置按 `owner_uid` 存在 `user_settings`，多账号各自独立，不会互相串。

## 3. 操作步骤（照做即可）

### 3.1 打开设置

右上角 **设置（齿轮）→ 应用配置** Tab。

### 3.2 找到「周报」的模块级 AI 配置

往下滚到 **AI 模型（模块覆盖）** 区域，展开「周报」模块。
（不要改上面的「AI 模型（全局默认）」——那是云端兜底。）

### 3.3 填三个字段

| 字段 | 填什么 | 示例 |
|---|---|---|
| **服务商** | 下拉选 **「Ollama（本地 / 局域网自建）」**（v1.0.42 起）；老版本选「自建兼容端点」 | `ollama` |
| **服务地址** | `http://<PC局域网IP>:11434/v1` | `http://192.168.31.182:11434/v1` |
| **模型名称** | 与 `ollama list` 完全一致 | `qwen2.5vl:7b` |
| **API Key** | **v1.0.42 起可留空**（内网自动用占位串）；老版本填任意非空串 | `ollama` |

地址写法注意：

- 必须带 `/v1` 结尾，**不要**带 `/chat/completions`（代码会自己拼）。
- 内网 IP 不写 `http://` 也行，`ensure_url_scheme` 会自动补 `http://`（公网才补 https）。
- 写成 `https://` 会 SSL 握手失败 → 明确用 `http://`。

> ⚠️ **v1.0.41 及之前**：前端保存按钮 `:disabled="!hasKey"`，后端 `build_recognizer()` 也会在
> Key 为空时返回 `None`（报「未配置识别服务」）。Ollama 不校验 Key 但契约要求非空，
> 填 `ollama`、`local` 或任意占位串即可，**不会产生任何费用**。
> **v1.0.42 起**：内网地址自动识别，可留空。

### 3.4 先「测试连接」再「保存」

点 **测试连接** → 显示「连接成功」后再点 **保存**。

测试连接会发一个最小请求 `{"model":..., "messages":[{"role":"user","content":"hi"}]}`，
验证 `地址 + 模型名 + Key` 三元组可用。失败提示已按 401/404/429 分类，按提示排查。

### 3.5 把「识别并发数」改为 1

**应用配置 → 通用设置 → 识别并发数**：从默认 `3` 改成 **`1`**。

理由：云端能并行 3 路，本地单张 8 GB 显卡并发 3 路视觉推理会显存溢出或极慢。
该项有 1~8 的范围校验，**修改后需重启应用生效**（设置页已注明）。

### 3.6 用一张真实截图验收

周报 → 任务上传 → 传一张真实工单截图 → 识别校对，逐项核对：

- [ ] 任务标题是否完整、没被截断
- [ ] 起止时间是否**原样抄录**（尤其跨天工单「11月2日 10:30 → 11月3日 12:19」）
- [ ] 状态、客户名是否正确
- [ ] 企微「一周小结」截图的会话数 / 分钟数能否识别成数字
- [ ] 识别耗时是否在 60 秒内（超时会标记为失败，可「重试失败项」）

**先小批量试，别一次传 20 张。** 本地 7B 模型的准确率需要你实际评估后再决定是否全量切换。

## 4. 双配置切换（推荐工作流）

| 场景 | 操作 |
|---|---|
| 日常省成本、数据不出局域网 | 周报模块用本地模型（模块覆盖层） |
| 遇到密集表格 / 模糊截图 / 跨天时间识别不准 | 设置里点周报模块的「恢复继承全局」→ 立刻回云端 `qwen3.8-flash` |
| PC 关机 / Ollama 挂了 | 同上，无需改任何地址 |

全局层始终保留云端 Key，所以**切换是秒级的，不会丢配置**。

## 5. 配置存储与安全

- 配置存在 NAS 的 `user_settings` 表（`${TRIM_PKGVAR}` 下，升级保留）。
- `api_key` **只写不读**：`get_ai_config()` 只回 `has_key` / `key_masked`，明文绝不回传前端；
  审计日志也排除了 `api_key` 字段。
- 服务地址、模型名会出现在前端（本来就要显示给你看），无敏感信息。
- ⚠️ 反向风险在 PC 侧：Ollama 无鉴权且暴露端口后，**局域网任何设备都能调用**。
  部署指引里已要求防火墙限定来源为 NAS IP，务必照做。

## 7. 故障速查（软件侧视角）

| 现象 | 最可能原因 | 检查 / 修复 |
|---|---|---|
| 「需先填写 API Key 才能保存」 | 前端 `hasKey` 校验 | 填任意占位串如 `ollama` |
| 测试连接：无法连接 / 超时 | PC 防火墙、`OLLAMA_HOST` 仍是 127.0.0.1、PC 休眠 | 见部署指引 §4；在 api 容器内 curl 验证 |
| 测试连接：404 | 地址多写了 `/chat/completions`；模型名与 `ollama list` 不一致 | 地址以 `/v1` 结尾；核对模型 tag |
| 测试连接：401 | 一般 Ollama 不会返回；若用 LM Studio/vLLM 且设了 key | 填对 Key |
| 连接成功但识别结果为空 / 全错 | 用了纯文本模型 | 换 VLM（`qwen2.5vl:7b`） |
| 识别返回 400 | ① 端点不支持 `response_format`（代码自动降级重试）；② **长截图 token 超过本地模型上下文**（本机实报，见下） | 看错误体：`exceeds the available context size` = 上下文超限 → v1.0.44 起自动缩放原图（见下） |
| 首批失败、后面成功 | 模型冷加载 > 60s | 预热 + `OLLAMA_KEEP_ALIVE=-1` |
| 显存溢出、耗时暴涨 | 并发仍为 3 | 识别并发数改 1 并重启应用 |
| 用了一周突然连不上 | PC DHCP 换了 IP | 绑定静态 IP，更新服务地址 |
| 切回云端后仍走本地 | 模块覆盖层还在 | 点「恢复继承全局」或 `DELETE /settings/ai/weekly_report` |

### ⚠️ 实报案例：长截图（企微一周小结）识别 400（2026-11-17 已修复）

**现象**：用户上传 `线上售后.jpg`（企微一周小结卡片），软件内调用本地 `qwen2.5vl:7b` 识别失败。
小尺寸合成图能识别，真实长截图必失败。

**取证**：用项目真实识别器 + 真实图片 + 完整 prompt 复现，拿到错误体原文：
```
{"error":{"message":"request (4663 tokens) exceeds the available context size (4096 tokens),
try increasing it","type":"invalid_request_error"}}
```
- 图片 1440×3136 长截图，Ollama 视觉编码器切成 **8 个 tile**（`decoding image batch 8/8`），
  每 tile 数百 token；加项目 prompt（1129 字符）共需 **4663 token**。
- 根因：RTX 4060 **8GB 显存** → Ollama 按显存自动设默认上下文 `num_ctx=4096`，超了 567 token。
- 这是**部署配置问题，不是代码 bug**；云端模型上下文大，不会有此问题。

**为何不在请求里改 num_ctx**：实测 OpenAI 兼容层请求里带 `options.num_ctx=8192` **不生效**（仍 400）；
只有 Ollama 原生 `/api/chat` 才认。项目走 OpenAI 兼容协议是为了同时兼容云端厂商与多种本地端点，
为单一服务的上下文限制改成原生 API 会破坏其他端点 —— 代价大于收益。

**修复分两步（均已执行）**：

*第一步 · 应急（v1.0.42 时代）*：给 Ollama 服务加 `OLLAMA_CONTEXT_LENGTH=8192`，先能用。
但代价是 KV cache 翻倍（200→400 MiB），8GB 卡显存余量只剩 **190 MiB**，批量处理隐患大。

*第二步 · 根治（v1.0.44，当前状态）*：软件端**发图前智能缩放**（`vision_image.py`）。
取证对照（同一张真实图，统一 4096 上下文）：

| 处理 | token | 结果 |
|---|---|---|
| 原图 1440×3136 | 4658 | ❌ 超 4096 → 400 |
| 只裁黑边（−3% 面积） | 4616 | ❌ 仍超 —— **裁剪几乎无效** |
| **等比缩放到长边 1536** | ~3100 | ✅ 通过，指标全对 |
| 缩到长边 720 / 400 | ~2350 / ~1200 | ✅ 连 400px 都全对 |

**关键结论：决定 token 的是像素总量（分辨率），不是内容裁剪。** Ollama 视觉编码器按固定
patch 切图，裁黑边只降 1% token；缩放才是有效手段。因此策略定为「长边>1536 才等比缩放」，
**不做智能内容检测/裁剪**（易误裁状态栏/二维码，且裁剪会引入坐标偏移风险）。

- 策略：小图**字节完全不变**（零损失）；透明 RGBA/LA **合成白底**；保持原格式与 MIME；等比不改变宽高比。
- 周报识别（`vlm.py`）与图片 OCR（`ocr.py`）共用 `vision_image.prepare_image`，口径一致。
- 音效：上下文**降回 4096**（`OLLAMA_CONTEXT_LENGTH=4096`，服务与自启任务均已改）——
  显存占用 **7767→6942 MiB，余量 190→1015 MiB**，批量处理余量充足。

**验证**：真实长图 + 项目完整 prompt + OpenAI 兼容层：
- PC 本机 7.6s（4096 上下文 + 缩放）、容器内见下；类型 `wechat_summary`
- 指标全对：`361 次会话 / 322 分钟 / 周一夜晚 9:29 / 11.9-11.13`
- 单测 415 项全绿（新增 11：小图字节不变/阈值/等比/透明白底/格式 MIME/禁用缩放等）

**以后注意**：缩放阈值常量在 `vision_image.py: MAX_IMAGE_EDGE`（默认 1536）。
若遇到密集小字被缩糊，调大该值；若有超长图仍报 400，调小该值（或临时把 `OLLAMA_CONTEXT_LENGTH`
调到 8192——但会牺牲显存余量）。透明图已自动白底处理，无需手工转换。

## 附：可脚本化的配置（可选）

若不想点界面，也可直接调 API（身份走网关头，真机上由网关自动注入）：

```bash
curl -X PUT "http://<NAS>/app/omnioffice/api/settings/ai?module=weekly_report" \
  -H "Content-Type: application/json" \
  -d '{
        "base_url": "http://192.168.31.182:11434/v1",
        "model": "qwen2.5vl:7b",
        "api_key": "ollama"
      }'

# 测试连接
curl -X POST "http://<NAS>/app/omnioffice/api/settings/ai/test?module=weekly_report" \
  -H "Content-Type: application/json" -d '{}'

# 切回云端（清除模块覆盖）
curl -X DELETE "http://<NAS>/app/omnioffice/api/settings/ai/weekly_report"
```

> `module` 参数用的是模块 id（`weekly_report`），可在 `/api/modules` 注册表确认。
> 真机上这些请求需经飞牛统一网关携带 `X-Trim-*` 身份头，浏览器界面操作更省事。
