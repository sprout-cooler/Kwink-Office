## 1. 出差主题：数据结构差异

### 1.1 与现有"客户""项目"的差异对照

出差记录是**有起止时间、有地点、有金额**的事务型实体，与其他维度本质不同：

| 维度 | 客户 | 出差（新增/增强） | 项目（当前不存在） |
|---|---|---|---|
| 生命周期 | 长期存在，可归档 | **有明确起止**，是时间段事件 | 长期存在 |
| 关键属性 | 名称/联系人/行业 | **出发地·目的地·经纬度·里程·交通方式** | 名称/周期/负责人 |
| 金额属性 | 无 | **有**（里程、差旅费） | 通常有预算 |
| 地理属性 | 仅有地址文本 | **有经纬度**，可在地图上连线 | 一般无 |
| 状态语义 | 合作中/暂停/归档 | 计划中/进行中/已完成/已取消 | 未开始/进行中/已完成 |
| 关联中枢 | 客户是中枢，出差挂客户下 | 出差 → 客户（可空） | — |

**关键结构差异**：出差**不是分类标签，而是带时间区间与坐标的事件**。因此它不能像 `stat_category`
那样塞进周报任务的分类列，必须独立成表（`biz_trips` 已存在），靠 `customer_id` 外键挂到客户。

**证据**：`models.py:258-296`（BizTrip 现有字段）。

### 1.2 新增字段清单

在 `biz_trips` 上新增 4 个字段（`biz_trips` 已有 `title/客户/起止/交通/里程/花费/status`，已覆盖"目的地、起止时间、报销"的大部分）：

| 字段 | ORM 列 | 类型 | 说明 |
|---|---|---|---|
| 出差事由分类 | `reason_code` | String(32) | 枚举：客户拜访/技术支持/售前演示/交付实施/培训/会议/其他 |
| 报销状态 | `reimburse_status` | String(16) | 枚举：无需报销/待提交/已提交/已报销 |
| 报销金额 | `reimburse_amount` | Numeric(14,2) | 实际报销金额，与 `cost_amount`（本次花费）区分 |
| 关联周报任务 | `report_task_ids` | JSON(list[int]) | 联动的反向指针，见第 3 节 |

**为什么用 `reason_code` 而不是自由文本**：与现有 `stat_category`/`status`/`transport` 一致的范式
（枚举 code 存库 + `capabilities()` 驱动前端下拉），保证筛选与统计可用。

**金额用 Numeric(14,2) 而非 Float**：与项目既有约定一致（财务表金额用 Numeric，避免浮点累加误差）。

**证据**：枚举范式见 `modules/biz_dashboard/constants.py:11-47` 与 `capabilities()`（`constants.py:100-115`）；
金额类型见 `models.py` 中 `biz_expenses` 的 `Numeric(14,2)` 定义。

### 1.3 前端改动

「出差与路径」Tab（`TripTab.vue`）：
- 新增出差记录表单增加：事由分类（下拉）、报销状态（下拉）、报销金额（数字输入）
- 表格增加：事由分类列、报销状态列、报销金额列
- 全部下拉选项**由后端 `capabilities()` 驱动**，前端不硬编码枚举

## 2. 客户来源字段

### 2.1 可选值与存储

**固定枚举**（存 code 字符串）：

| code | 显示 | 含义 |
|---|---|---|
| `referral` | 老客户介绍 | 现有客户转介绍 |
| `bid_win` | 招标中标 | 参与招投标中标 |
| `campaign` | 市场活动 | 展会/发布会/线上活动 |
| `outreach` | 主动开发 | 销售主动触达 |
| `channel` | 渠道推荐 | 代理商/集成商推荐 |
| `other` | 其他 | 需补充说明 |

**存储方式**：
- `biz_customers.source`（String(32)，默认 ""）存 code
- `biz_customers.source_note`（String(255)，默认 ""）存补充说明 —— **仅当 source = "other" 时前端显示**
- 枚举在 `constants.py` 定义 `CUSTOMER_SOURCES`，经 `capabilities()` 下发

**为什么"其他"要配自由文本**：纯枚举无法覆盖真实业务；纯自由文本则无法统计与筛选。
组合方案兼顾两者，且 `source_note` 只在 other 时有值，不污染其他记录。

**为什么 source 存 code 而非中文**：code 稳定（中文文案可随时改），筛选与统计用 code。

**为什么客户表 name 不加唯一约束、来源也不加**：与 `BizCustomer` 既有设计一致 ——
同名客户可能是不同主体（总公司/分公司），强约束反而制造录入障碍，重复由应用层提示。

**证据**：`models.py:231-234` 明确写"name 不加唯一约束：同名客户可能是不同主体…重复由应用层给出提示而非阻断"。

### 2.2 前端改动

「客户管理」Tab（`CustomerTab.vue`）：
- 新增客户/编辑客户表单增加「客户来源」下拉（选项来自 `capabilities().customerSources`）
- 选中"其他"时，下方展开「来源说明」输入框
- 客户列表增加「来源」列（显示中文标签，非 code）
- 支持按来源筛选

## 3. 周报联动方案（AI 抽取客户名 → 反推来源）

### 3.1 联动方向

```
周报截图 ──AI 识别──> task_items（含 extra.customer_name）
                              │
                              ├── 人工校对（ReviewTab 可改）
                              │
                              ▼
                    匹配 biz_customers（同账号内按名称匹配）
                              │
                              ▼
                    ① task_items.extra.customer_id  ← 反向指针
                    ② biz_customers.source 若为空 → 用「周报关联」自动标记
```

**方向是单向的：周报 → 客户**。不反向写客户主数据（除来源的**空值填充**外）。

### 3.2 AI 抽取客户名：怎么让模型知道客户有哪些

这是本方案的技术核心。`vlm.py` 的 `PROMPT_V3` 是**静态提示词**（`vlm.py:23-60`），
当前只让模型抽 title/时间/status，不涉及客户。

**做法**：识别时把该账号的**客户名清单**注入提示词，让模型在客户名清单里做**指认**，
而不是自由发挥抽取字符串。

```
已知客户名单：XX科技、YY集团、ZZ制造
若任务内容明确提到某个客户，在该任务的 "customer" 字段填该客户的**原名**；
若涉及多个客户，用顿号分隔；若无客户线索，填空字符串。
```

**为什么用"指认"而非"抽取"**：
- 抽取自由文本 → 会出现"XX科技公司"、"xx科技"、"XX 科技"等变体，与 `biz_customers.name` 对不上
- 指认（限定在给定名单内选）→ 输出天然可与客户表精确匹配
- 名单为空时**不注入该段**，退回纯抽取行为（客户都还没建，抽了也对不上）

**实现路径**（已核实可行）：
1. `recognize_queue._process_one` 已持有 `uid = shot.owner_uid`（`recognize_queue.py:143`）
2. 在 `recognizer.recognize(shot.stored_path)` 调用处（`recognize_queue.py:162`）查该账号客户名，传入
3. `vlm.py` 的 `recognize`/`_call` 增加 `customer_names: list[str]` 参数，动态拼接提示词
4. `PROMPT_V3` 保持不变（作为无客户时的基础版本），新增 `PROMPT_WITH_CUSTOMERS` 变体

**代价**：提示词变长、token 成本上升。**控制措施**：客户名清单限长（建议 ≤ 100 个，超出截断并告警），
避免客户上千时提示词爆炸。

**跨模块依赖**：`weekly_report` 需要读 `biz_dashboard` 的 `BizCustomer`。
当前**不存在**这种跨模块引用（`grep -rln BizCustomer` 只命中 models.py 与 biz_dashboard/service.py）。
处理：客户名查询下沉到 `db/models.py` 层面（直接用 ORM 模型），不 import biz_dashboard 的 service，
保持模块间只依赖数据层，不耦合业务层。

### 3.3 数据映射

| 周报侧（task_items） | 客户侧（biz_customers） | 映射规则 |
|---|---|---|
| `extra.customer_name`（AI 指认的原名） | — | AI 输出的客户名原文 |
| `extra.customer_id` | `biz_customers.id` | 同账号内按 name 精确匹配；匹配不到则留空 |
| `extra.customer_match` | — | `matched` / `ambiguous` / `none`，供校对界面提示 |
| — | `biz_customers.source` | **仅当 source 为空**时，若该客户被周报关联，填 `weekly`（周报关联） |

### 3.4 去重与覆盖规则

| 场景 | 规则 | 理由 |
|---|---|---|
| 同名客户（账号内 name 相同有 2 条） | **不自动关联**，`customer_match = "ambiguous"`，`customer_id` 留空，提示人工在 ReviewTab 指定 | 猜错会把工时算到错误客户名下，财务影响大 |
| AI 抽出客户名但客户表无此人 | `customer_match = "none"`，**不自动创建客户** | 自动建客户会产生一堆脏数据（同名变体、错别字），且客户是财务主数据，污染代价高 |
| 人工在 ReviewTab 改了客户 | 人工值优先，**覆盖** AI 值；`customer_match = "manual"` | 人工校对是最终裁决 |
| 重新识别同一张截图 | 先 `db.query(TaskItem).filter(screenshot_id == sid).delete()` 清旧任务再重建（现有逻辑 `recognize_queue.py:207`） | 保证不产生重复记录 |
| 客户名在客户表被改名 | `task_items.extra.customer_name` 保留**识别时的原名**（不改），`customer_id` 不变 | 改名是主数据维护行为，不该篡改历史识别证据 |
| 客户被删除 | `customer_id` 外键置 NULL（`BizCustomer` 已有删除时解绑逻辑） | 避免指向空气的关联 |

### 3.5 手动录入 vs 自动同步的优先级

**优先级（高 → 低）**：

1. **人工校对值**（`extra.customer_match = "manual"`）—— 最高，永不被覆盖
2. **人工在出差/财务模块直接选客户** —— 本来就是显式主数据操作，最高优先级
3. **AI 指认 + 唯一匹配成功** —— 自动填充
4. **无客户线索** —— 留空

**"客户来源"字段的填充优先级**：

1. 用户在新增客户时手动选 → **最高，永不被自动覆盖**
2. 手动值留空 + 客户被周报关联 → 填 `weekly`
3. 留空且无周报关联 → 保持空

**关键约束：自动同步**只填空、不覆盖**。理由：客户来源是**业务判断**（这个客户怎么来的），
AI/联动只能提供"这个客户在周报里出现过"这一**弱信号**，不足以推翻人的判断。

**反向写入的依据**：客户来源是主数据的**业务属性**，周报只提供"该客户在周报中被提及"这一事实。
把事实转成"来源=周报关联"是合理推断，但仅在字段为空时才填。

## 5. 数据一致性与重复记录风险

| # | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| 1 | **客户名歧义** —— 同名客户导致工时/费用挂错客户 | 🔴 高 | 不自动关联歧义项（`ambiguous`），留空并提示人工指定；人工值为最终裁决 |
| 2 | **AI 抽错客户名** —— 截图模糊/简称导致误配 | 🟠 中 | 限定在客户名单内"指认"而非自由抽取；输出原名供人工比对；ReviewTab 可改 |
| 3 | **自动建客户造成脏数据** | 🟠 中 | **不自动创建客户**（`none` 状态只提示"该客户未建档，是否新建"由用户决定） |
| 4 | **重复识别产生重复任务** | 🟢 低 | 现有逻辑先 delete 同 screenshot_id 的旧任务再建（`recognize_queue.py:207`） |
| 5 | **客户改名后历史关联断裂** | 🟢 低 | `customer_id` 外键不随改名变化；`customer_name` 保留识别原名作为证据 |
| 6 | **客户删除后指向空气** | 🟢 低 | 复用 `BizCustomer` 既有删除解绑逻辑；`customer_id` 置 NULL |
| 7 | **来源被自动值覆盖** | 🟡 中 | 自动同步**只填空不覆盖**；手动值优先 |
| 8 | **提示词随客户数膨胀** | 🟡 中 | 客户名清单限长 100，超出截断；客户表为空时不注入该段 |
| 9 | **周报与出差的客户不一致** | 🟡 中 | 出差用 `customer_id` 外键（强一致）；周报用 `extra` 存 id+name（弱一致，人工校对兜底） |
| 10 | **老库加列失败**（PG NOT NULL 无 DEFAULT） | 🟡 中 | 实现时实测 PG 与 SQLite 两条路径的迁移 |
| 11 | **客户名含分隔符/特殊字符** | 🟢 低 | 名单以 JSON 数组传入提示词，不做字符串拼接注入 |
